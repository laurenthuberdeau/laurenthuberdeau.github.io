# Agentic Session Simulator

Agentic session simulator demonstrates the feel of the different phases of LLM inference.
That is, prefill and decode. The simulator allows configurable prefill and decode speed,
with a N-point curve to simulate the slowdown that accompanies longer sessions, and a
request latency option to simulate a system under contention.

Ships as an all-in-one HTML file, with query parameters allowing a quick linking to
a predefined configuration.

Session export and replay is not implemented yet, so this pass ships eleven built-in session
corpuses instead: `greenfield`, `bug-hunt`, `long-log`, `deep-fix`, `sweep`, `oncall`,
`migration`, `refactor`, `doc`, `repro`, and `audit`. Each is pure data and each exercises a
different shape of the same model — see [`scenarios.md`](scenarios.md).

## Layout

The page is authored as four files under `src/` and **built** into the single artifact:

| file | holds |
|---|---|
| `src/index.html` | markup, plus the pre-paint theme script that has to run in `<head>` |
| `src/app.css` | the stylesheet |
| `src/scenarios.js` | the `SESSIONS` corpus — data only |
| `src/app.js` | the model, the views and the controls |

```sh
node tools/build.mjs           # write index.html
node tools/build.mjs --check   # exit 1 if index.html is not what src/ says it should be
```

**Edit `src/`, not `index.html`.** The artifact is regenerated wholesale, so a hand edit to it
looks right, works right, and vanishes on the next build — which is why the selftest fails when
the two drift apart (`index.html is the current build of src/`).

The build joins the sources at marker comments — `/* inject:css */` and `/* inject:app */` in
`src/index.html`, `/* inject:scenarios */` in `src/app.js` — rather than concatenating whole
files, so the output is byte-identical to the original single file: `'use strict'` is still the
first statement of the script and the corpus still sits exactly where it sat.

## Running

Open `index.html`. No dependencies, no network, and no build step at read time — building is for
editing only.

```sh
open index.html
```

The defaults are the `local` preset with the prompt cache on. The engine card also carries four
presets — `local`, `API`, `API (fast)`, `ASIC` — for the machines people actually run against, see
[Engine presets](#engine-presets). This file quotes no run figures: every duration and ratio belongs
to the engine settings, so the summary card states them for the run in front of you and they move
with the sliders.
Add `speed=4` for a quicker look, or `session=greenfield` for a
small-context one.

The page opens parked at zero rather than running at you: the transcript, the summary and the
request table are all drawn for `t = 0`, and *run* (`space`) starts the clock. Add `autoplay=1`
for a page that plays itself.

## Model

Every model turn is one request, and every request pays four phases in order:

| phase   | cost                                                              |
|---------|--------------------------------------------------------------------|
| queue   | `latency` ± `jitter`, once per request                              |
| prefill | `new tokens / (prefill * curve)`, the cached prefix being free      |
| decode  | `1 / (decode * curve(context))` per output token, reasoning or prose |
| exec    | the tool runs; its output joins the context of the next prefill      |

Context starts at the session's boot tokens (system prompt, tool schemas, repo map) and
grows with every message and tool result, so later requests get slower at both phases. The
decay curve is one piecewise-linear N-point multiplier over context size that prefill and
decode share — a longer prompt costs more per token whether the work is ingesting it or
generating against it — editable by table or by dragging points on the chart. Prefill is
charged in 512 token blocks so the curve is integrated rather than sampled once, which also
happens to be how engines chunk it.

Tokens are counted by splitting text where an engine would, and then in fives. Every punctuation or
symbol character is its own token (`foo-bar` is `foo`, `-`, `bar`; `"foo"` is `"`, `foo`, `"`) and a
run of digits splits off from the letters around it (`port8080` is `port`, `8080`); whatever piece is
left longer than five characters is cut into fives, so `the` is one token, `compaction` two and
`invalidates` three. That is an approximation of a BPE tokenizer — a real one splits on learned
merges rather than at a fixed five — but it prices a long JSON blob and a shell one-liner
differently, which one token per word could not. Tool results too large to embed carry an
explicit `simTokens` inflation, and are shown as an elided preview that still counts in
context.

### Chain of thought

A step may carry a `cot` trace — the reasoning the model emits before it answers. It is not a
fifth phase: reasoning is generated by the same decode loop at the same throttled rate, so it
appears on the bar as decode and in the transcript as dim text above the answer it produced.
What it delays is the first token *shown*, which is why a thinking model feels slow to answer
even when the engine is idle.

It is billed as any other generated token: it costs decode time, and it stays in the history, so
it is re-read on every later turn the way a harness that echoes thinking blocks back re-reads it.
The re-read is the small part — prefill runs far faster than decode on a local engine, and
the cache usually skips it — so the price of a trace is mostly the seconds it spent being written.

The `audit` corpus is the case where that is the whole story: three quarters of what the model
generates is reasoning, so the run spends most of its wall time streaming text the transcript
shows in gray, and the summary reads decode-heavy while the transcript looks nearly idle.

### Cache

The prompt cache is on by default, which makes prefill incremental: a request ingests only
what arrived since the last turn — the newest tool result, the newest instruction — and reuses
the attention state already held for everything before it. Reads are treated as instant,
which is the local-inference case, where the KV cache stays resident and is not shared with
other users. Nothing is charged for the prefix and nothing expires; unticking the cache is
what a shared endpoint with no prefix reuse looks like.

One thing *does* expire the prefix: context compaction. A coding harness that runs long
collapses its history to a summary mid-session, and a summarised history is not in the KV
cache. The corpus can model that with a `compact` step: the timeline drops context back to the
boot prompt plus the summary and treats everything past boot as fresh, so the next request
re-prefills it at full cost — the boots stay cached, the rest is paid for again. `deep-fix`
runs one of these mid-way; the transcript shows the harness step (`context compacted · 69k →
6.3k summary`), and the summary adds `peak context` and `harness compactions` rows so the
drop — and the cache rebuild — is visible at a glance.

The difference is most visible on the turns that follow something small. A request that arrives
after a two line diff prefills that diff and nothing else, where an uncached engine is still
re-reading the whole history; `long-log` is built out of those turns, and the summary's
`prefill (cached)` row is what they add up to.

What caching does *not* rescue is throughput. The fresh chunk still attends to the whole
history, so it pays the curve wherever the session has reached: effective prefill and decode both
fall, request by request, as the context grows. Caching skips work on the part of the prompt the
engine has already ingested; the curve taxes the new tokens by how much history they have to
attend to.

## Controls

### The guide

The page opens on a panel that says what it is: the four phases a turn splits into, how the page is
worked, the two sessions to start with, and then the options the engine offers and the keys that
work it — the last two being what the body scrolls to reach, so the picker is the last thing put in
front of you rather than the last thing the panel has. It is not a tour you get once — the **`?`**
in the header brings it back, and its ✕, a click on the backdrop or `esc` puts it away. The phase
names carry the same colours the bands wear, and every option it lists is held to the field in the
settings panel that changes it, so the panel cannot advertise a dial nobody built.

It also offers a starting point rather than an empty page, because the one thing a first reader
cannot guess is that prefill and decode pull in opposite directions. Two cards, two ends of the
corpus:

| card | loads | the turn it stands for |
|------|-------|-----------------------|
| **decode-heavy** | `greenfield · small context` | a chat-shaped turn: small prompt, long answer |
| **prefill-heavy** | `long-log · context blowout` | a wall of context re-read every turn to produce a paragraph |

Both are *measured* when the panel opens, at whatever the sliders say, the same way the picker
measures its rows — the card quotes the run you would get, not a profile it was authored against.
Choosing one loads that scenario **and starts it**: the page opens parked because it should not
start by itself, not because pressing a button should do nothing. The rest of the corpus is one
click further, in the picker. It stays down when a link carries `?intro=0` or the page is told to
`autoplay`, and nothing about it is stored: the page is a file you open from disk, which is an
opaque origin a browser may refuse storage to, and a guide you cannot get back to is worse than one
you see twice.

### The run

Under the header, one rectangle says what the engine is doing right now. It names the phase,
takes that phase's colour — heading, a stripe down its left edge, and a wash that fills as the
phase itself progresses — and carries the numbers for it: `prefill · req #4 · 5.9k / 12k tok
ingested · 118k reused @ 1.4k tok/s`. Four boxes, one per phase, would have been mostly idle
space, so the phase that is not running simply is not shown. The times between phases get the
same rectangle with the neutral treatment: the bar reads *harness overhead* for the time the
harness spends between turns, which belongs to neither the engine nor the tool, and before you press
run and after the last token the bar
reads `idle` and `run complete` rather than pretending something is still streaming.

**Click it to step.** The bar jumps the playhead across a phase boundary — `click` forward to the
next one, `shift-click` back to the one before the phase you are in — and its right-hand hint names
where a click lands (`→ prefill · 8.62s`, or `→ end of run` when there is nothing left). It lands
on the same boundaries the seek bar is painted from, so it walks the run band by band: queue,
prefill, decode, tool exec, the harness overhead after it, the next request. Every step leaves the phase the bar
is naming, because a boundary belongs to the band that starts there: standing on the start of the
band you are already inside would leave the heading, the colour and the wash untouched, and the
control would look dead — which is what a step back used to do from inside any band shorter than
its own threshold, that is from every queue wait and every stretch of harness overhead, on every click. That is how you
compare one prefill against the next without trying to hit the edge of a band with the pointer; the
seek bar itself still scrubs freely by click or drag.

`space` play/pause · `R` restart · `←` `→` seek one second (`shift` for five) ·
`1`–`7` playback speed · `esc` close the panel in front. The transport keys are mute while a panel
is up: a transport you cannot see is a transport you do not move. And `space` is the transport's
however the caret got where it is — a click leaves it on the button that was clicked, and a closing
panel hands it back to the button the panel was opened from — so a button that answered space would
replay the last click: dismiss the guide, press space, and the guide comes back instead of the run
starting. The button gives the caret up when it takes the key, so one press is one action, while
`enter` stays the focused control's own key and, inside a panel, so does space — which is how the ✕
and the session rows are worked.

A panel closes from its own controls — the ✕ in the corner, a click on the backdrop behind it, or
`esc` — and `esc` takes the panel on top and only that one, so escaping the session list leaves the
guide behind it where it was. The lock on the page holds until the last one leaves.

Below 900px the settings card stack stops being a sidebar and becomes a second view: the
**settings** button swaps the session and the panel for each other, and whichever is up
takes the whole space under the phase bar. Stacked, the summary started a screen below the bar
with the boot step still peeking over it and neither half was tall enough to read. On a narrow
window the session gets that space when the page loads, so opening settings is your move, not
the page's.

The transcript follows the run by itself. A message that is still streaming is kept at the end
of the pane, where its newest line is, and the pane reserves a cushion below its content so
that line rests on space instead of on the bottom border — the message being written sits
about three fifths of the way down the pane, which is where you are reading it from. A block
that arrives all at once — a tool result, the next user message, a compaction — is placed by
its *first* line instead, because the long results in these corpuses are taller than the pane
and pinning their bottom would drop you into the last screenful and never show the beginning.
Scroll up and the pane is yours again; return to the bottom of the scroll, or move the
playhead by any route — the seek bar, a click on the phase bar or on a request row, `←` `→` —
and the sim takes it back. It knows its own scrolls from yours, so following a tall block by
its first line does not read as you having taken over.

That cushion is the pane's whole bottom padding, `min(40vh, 260px)`, and both halves of the
`min()` are load-bearing. A scroll container counts its own padding in its scroll height, so
an unbounded `40vh` would lift the newest line off the top of its own pane on a short window —
and this pane used to carry `26vh` for no reason at all, wearing a scrollbar on a session of
three short messages — while a flat `260px` is no cushion on a tall one. What it costs is the
thing the bar reports: a session short enough to fit still has something to scroll, and the
last part of what it scrolls is rest rather than text.

Nothing in a message shows up before the stream produces it, and not only out of sight: a
block the run has not reached is out of the *layout*, so the pane's height is the session as
far as it has been told, plus the one cushion under it that belongs to no message. Nothing
above the bottom of the content is room the run has not earned, and the end of what the run
has told is where the pane comes to rest — which is what a requests row scrolls to. It also
means the pane has to be told never to follow a block that is not revealed: one with no box
reports a rect of nothing, and the pane would lurch to its top. The framed **tool call** box —
the block that reads `tool call · Bash` over the arguments as they are generated — is built
along with the message but stays hidden until the model starts emitting it: its first argument
token, or for a call with no arguments the moment the prose before it ends. So it never sits
framing nothing through queue, prefill and the prose half of decode. That is the one thing a
replay should not give away early: in a real session you learn the model reached for a tool
when it starts emitting the call, not while it is still writing the sentence that leads up to
it. Seek back past the message and the box goes away again with its tokens; a finished run
shows every call it made.

The **session summary is the first card in the
panel**, because it is the thing you come back to after every settings change: it leads with
`total` and `prefill : decode` — the split between the two faces of inference — then the phases,
the context, and what the prompt cache avoided. Three rows share one shape, a token count with the
time it took in parentheses, so the card reads as columns:

```
prefill             <tokens> tok  (<time>)
prefill (cached)    <tokens> tok  (<time>)
decode              <tokens> tok  (<time>)
```

The **requests history is the second card**, directly under the summary rather than at the far
end of the panel: its rows are the per-request detail behind those totals, and both cards
re-render on every settings change, so they are read together without scrolling.

The request table answers a question its own numbers cannot — *which message is this?* — so a
row is a link into the transcript, and the link is only a seek. The clock goes to that
request's last token and the pane does for it what it does for the playhead anywhere else:
follow to the end of what the run has told. That is the whole implementation, and it lands
where you meant because of the two rules already there — nothing the run has not reached has a
box, so there is no blank to land on, and a request's last token is the one instant its
message is entirely there. So a row clicked while the session is still parked at zero reads
that request in full instead of scrolling to an empty pane, and tabbing to a row and pressing
`enter` does what the pointer does. Because it is a seek rather than a new kind of navigation,
the run keeps whatever it was doing: clicked mid-decode it does not pause, the message comes
up finished and the run plays on past it. And because the pane shows where the run got to
rather than the beginning of a block, a message taller than the pane comes up on the line its
request ended on — the same rule that holds any streaming message rests at the end of the pane
on its cushion — and you scroll up from there to read it from the start. Each row carries that
on hover, and takes the pointer.

`prefill` is what the engine had to ingest and `prefill (cached)` what it did not, sitting
under the cost it answers rather than at the end of the card where it would be read long after
the reader stopped looking at the prompt. The `(cached)` row belongs to the cache, so with the
toggle off it is gone and `prefill` becomes the whole prompt — `411k tok (7m 11s)` for the same
`long-log` run, the two rows above added back together. That is why the toggle does not get a
row of its own any more: those rows show the state, where the old `prompt cache: on · instant
reads` line only restated the switch above. Each row pairs its tokens with its time, so the two
`avg` rows below are the division of two numbers you have just read, not another thing to
remember. The split is measured from the timeline, so it always describes the run on screen.
Every row has a hover note — the cursor goes to `help` over the card — because the panel is where these
definitions live: which tokens each rate counts, what the cache does and does not make free, and
why the phases need the harness overhead to add up to the clock. Then the panel holds the engine
card, which **opens** with the preset row — a machine as prefill, decode and request latency — and
then the two speeds, the prompt cache toggle, contention (the
request wait) as a group under the same heading, and the decay curve as a third such group. The presets lead the card because picking a machine
is what the card is for, and a shortcut sitting below the three sliders it moves is one you find only
after you have already hunted them. It is a group heading and buttons in the same idiom as
`contention`, and the pressed button is a read-out rather than a stamp: it marks
the machine all three of its fields still sit on, so a slider moved afterwards leaves none marked.
The labels are names alone — `local`, `API`, `API (fast)`, `ASIC` — four equal quarters of the 372px
panel on one line, each button two lines tall so the longest name wraps inside its column rather than
widening it,
and what each one is — the kind of machine, in words — is on its hover note, while the three numbers it
writes stay in the fields below the row, where a number carries a unit and can be edited. Every control
in it carries a **hover note of its own**, the same way the
summary rows do — one note per row, on the row itself, so the name, the field, the unit and the
slider all answer the same hover by inheritance. The name is a caption rather than a label
pointing at the control, because a browser suppresses the title tooltip on exactly that element,
and it is the one thing you hover to learn what a setting means. The control keeps its accessible
name through `aria-labelledby`; what that trades away is click-to-focus on the name, so the field
and the slider are clicked directly. Prefill and decode name what their rate counts and say it
decays as the context grows, following the decay curve; the cache toggle says what the engine
stops re-processing and that a compaction invalidates it; the request wait says what the engine
waits on before it starts work, and the jitter answers for itself inside the row because the
nearest note is the one you get. The summary card reuses the same vocabulary loosely — it speaks
of `prefill tok/s × the decay curve` where the engine card says the speed "decays as the context
grows" — and the two are deliberately free to phrase things differently. One documentation
mechanism for the whole page — native, on
hover, `help` cursor to say it is there — rather than a bubble of the page's own that only half
the surface uses. The line under the controls stays what it always was: `TTFT ≈ queue + prefill +
decode 1 token`, with its own note on the terms. The decay curve then closes that same card, as a
group in `contention`'s idiom rather than the card after the one it has to be read against — it is not
a setting beside the two speeds but the shape of both of them, each being a rate *at a point on this
curve* — and it opens the same way: `flat`, `gentle`, `steep` and `cliff` as four equal
columns above the chart they redraw, then the chart, then the points table, then **`+ point`** spanning
the row under the table — an action on the table rather than a preset, so it is not in the row with the
four. Both rows take their equal columns from one `.presets` rule; only the engine row is two lines
deep, because only its labels need the second. What a curve name does not spend on a second line it
spends on a hover note of its own, the same one line of prose the engine names carry: what the shape
does to a run, then the numbers it turns on, in the units the axis under them prints — taken from the
same entry of `CURVES` as the points, so a name and the shape it loads cannot be edited apart. What a
preset *writes* is a fact about the row rather than about one of its four options, so each row says it
once on the caption above the buttons and no button repeats it. Both are read-outs too: the shipped curve is a named
preset — `steep` — and the card opens with that one marked, because the row marks a preset only while
the curve is still point for point that preset, so dragging a point, typing one or pressing
**`+ point`** leaves none marked until a preset is pressed again. In the requests history, the
`prefilled` column shows how many prompt tokens that request actually had to ingest. Curve table cells commit
when the field loses focus, or on `enter`; `escape` puts the old number back. Nothing plays
itself unless it is asked to: the page loads parked, and any change to a session setting —
a speed, the cache, the latency, the curve, the scenario — pauses the clock immediately
rather than leaving the run moving under the edit; switching scenario also rewinds to zero
rather than rolling straight into the new run. Playback speed and the theme are not session
settings in this sense and do not pause, so `autoplay=1` governs the page load only.

The seek bar is the timeline drawn to scale rather than a progress fill: one band per phase
run, in that phase's colour — queue white, prefill amber, decode green, tool
exec purple, harness overhead neutral — dimmed ahead of the playhead and full strength behind it,
the playhead itself taking the colour of the phase it sits in, the same encoding the phase bar
above wears. Queue gets the absence of
colour because nothing happens to your prompt while it waits for a slot, and prefill the
amber because at bar height blue prefill sat too close to green decode to tell apart; the
light theme inverts white queue to a dark neutral, white on white being no band at all.
Bands are sized by duration, so the 147 s of prefill in a 177 s `long-log` run claims four
fifths of the bar and the bar shows where a run actually goes; hover a band for its phase, request number, and
own duration.

## Engine presets

The engine card carries four named machines, because the settings that describe a device only make
sense as a set — the same prefill speed is a different machine depending on the wait in front of
each request, and hunting that across three log sliders is not a way to compare devices. A preset
writes **prefill, decode and request latency**, in tok/s and ms:

| preset      | prefill | decode | request latency | reads as                                          |
|-------------|---------|--------|-----------------|---------------------------------------------------|
| `local`     | 750     | 50     | 300 ms          | a model on your own hardware, the one the page ships on |
| `API`       | 10k     | 75     | 3 s             | a hosted frontier API — fast reads, a round trip on every request |
| `API (fast)`| 10k     | 250    | 1 s             | the fast API tier, a DeepSeek V4 Flash class model — fast reads and a much faster stream |
| `ASIC`      | 20k     | 10k    | 500 ms          | fixed-weight inference silicon, where the run becomes tool-bound |

The decay curve, the jitter and the prompt cache are **not** part of a preset: they belong to the
deployment rather than to the hardware, so pressing one leaves them where you had them. A preset is
a shortcut rather than a mode — it writes the fields like any typed value, nothing is remembered,
and the button reads as current only while all three fields still match it, so moving a slider takes
the page off the machine it names. That is also why there is no `profile` parameter below: a link
copied after a preset is pressed carries `prefill`, `decode` and `latency` and replays identically
without knowing a preset was ever touched.

## Query parameters

| parameter             | meaning                                             |
|-----------------------|-----------------------------------------------------|
| `session`             | any scenario id — `greenfield`, `bug-hunt`, `long-log`, `deep-fix`, `sweep`, `oncall`, `migration`, `refactor`, `doc`, `repro`, `audit` |
| `prefill`             | prefill speed in tok/s, `50`–`100000` — the floor is a laptop doing something else, not a typo |
| `decode`              | decode speed in tok/s, before the curve, `1`–`10000` — the ceiling is the fastest preset |
| `cache`               | prompt cache, `1` on (default) or `0` off            |
| `latency`             | queue wait in front of each request, in ms, `0`–`120000` |
| `jitter`              | ± jitter on that wait in ms, `0`–`60000`, drawn from a fixed seed  |
| `curve`               | `flat`, `gentle`, `steep` (default), `cliff`, or `ctx:mult` points such as `0:100,32000:60` |
| `speed`               | playback speed `0.25`–`16`                           |
| `autoplay`            | `1` to play on load — parked at zero by default, and switching scenario always pauses   |
| `intro`               | `1` (default) to open the guide on load, `0` to leave it down — `autoplay=1` also leaves it down |
| `theme`               | `dark`, `light` — defaults to your OS preference unless set      |

```
index.html?session=long-log&prefill=60000&decode=240&latency=2500&jitter=1500&cache=0&curve=cliff&speed=4
```

One source holds those bounds, so the URL parser, the fields, the sliders and their clamps cannot
agree with each other: a link that carries something outside them is clamped into them on load and
the field shows what the link became — `?prefill=10` is the floor, 50 tok/s, and `?prefill=1e9`
is 100k.

## Tests

`tools/selftest.mjs` runs the page script in node against a small DOM shim, sweeping the
timeline and firing the transport, keyboard, settings, engine preset, curve editor, and seek
handlers. A preset is the one place the panel can put a number in the model that no field was asked
for, so every button is clicked and its three settings read back twice — from the model and from the
field the reader sees — while the jitter, the cache and the curve are compared before and after to
prove a preset touches only what it names. The label is the machine's name alone, so the hover note
is the only place the page tells a reader what kind of machine a button is: any figure that note quotes
is read back — "10k tok/s prefill", "3s request latency" — and held to the values behind the button,
since a note quoting the wrong speed is a machine the panel promises and the run does not deliver, while
a note that quotes no figures at all is left to its prose. The curve row is held the
same way: every number a curve note states has to be a point that curve draws — a note may name fewer
points than the curve has, never one it has lost — and each row's claim about what its preset writes is
tested by clicking all four and reading back every field they do not own. That claim is also held to
its place, on the caption of its row and nowhere else, since eight buttons ending in the same clause is
one sentence said eight times. The two rows share one length ceiling as well, so a preset added later
is written to the same length as the ones beside it rather than growing the paragraph back. The row is also held to
the width the CSS gives it — four equal columns of the fixed panel, each label fitting two lines of its
column and no word longer than one — and to the card's order, so the presets stay
at its head; and the pressed state has to let go the moment a field stops matching it.
It boots
the guide first, because that is what the page shows first: it must open on load and stay down when
`intro=0` or `autoplay` says to, offer exactly the two shapes it claims (the decode-heavy card has
to be dominated by generating and the prefill-heavy one by reading, measured on the corpus, or the
label over the card is a lie the card still tells), quote numbers that move when the sliders move,
load and start the scenario it names, mute the transport while it is up, and answer every single key
it advertises — documentation is the first thing to outlive the code it describes, so the rows of its
shortcut list are read back out of the markup and each one held to the handler that answers it; a key
that leaves the code cannot stay in the guide. The two panels are dismissed with the keyboard on top
of that: `esc` has to close the one in front and leave the one behind, hold the lock until the last
panel is down, stay mute over a run it must not start, and do nothing at all when there is no panel
to go back from. Neither key is decided by what the reader clicked last: space has to work the
transport with the caret sitting on the button they last pressed, hand that button's focus back so
the browser's own activation does not click it a second time, and still leave `enter` — and space
behind a dialog — to the control under the caret. Reading the caret at all needs a shim that knows
what it is sitting on, so it reflects the markup's start tags now, element names and `hidden`
alike: without the names `#panelToggle` answers as the div the shim invents for every id rather than
the button the page has, and without `hidden` every closed panel reads as open, so a page properly
locked behind a dialog looks like a dead keyboard. The same reading holds its list of engine options
to the settings fields that change them, their order to the rule that the panel's one choice stays
above the prose you scroll to, and its four phase dots to the variables the bands are
painted from. It also checks the seek bar's bands: they tile the duration with nothing doubled or
missed, each
band's phase is the one `phaseAt` reports at its midpoint, and every band phase has a colour
in both themes — so the bar cannot drift from the phase bar or go invisible on one palette. That
bar is read back at the centre of every band too: whatever colour the timeline is painted, the
bar standing over it has to name the same phase, and every state it can wear must have a colour
rule and a heading of its own, or it would render grey-on-grey and look like a dead control. Its
stepping is checked the same way — click from zero must land on each band start in turn, must
stop at the end of the run rather than wrapping, and `shift-click` must walk back the same
boundaries in reverse, including from a boundary itself, where a naive implementation would be a
no-op. It is stood in the middle of every band too, which is the case that used to fail: a step
back had to leave the phase it was standing in and name the one before it, not stop on that band's
own start, where the bar reads exactly as it did before the click.

The transcript's follow is measured against a synthetic layout, because the shim has no box
model: the test gives the pane a height, stacks the blocks, lets a block's reported position
move with `scrollTop` the way a scroll container's does, and — the way the page's CSS has it —
gives a box only to a block the run has reached. So the checks that the layout is honest come
first: at zero only the boot prompt and the first instruction have boxes and the pane has
nothing to scroll, and while a tool runs its result has no box at all and the pane does not
move. A block that arrives whole must then end up with its first line at the top of the pane,
and a block still streaming must end with its live line on screen — and because the shim's
tool results are made taller than the pane, the second rule cannot be satisfied by the
shortcut of pinning the bottom of the transcript, which is what the follow used to do. The
requests history is measured on the same layout, and what it measures is one seek: from parked
at zero, mid-run and at the end, a row must leave the clock on its request's last token and
that message the newest block in the pane with its live line on screen, and must give the
keyboard the jump the pointer gave while keeping the header row a no-op. Clicked mid-decode
while the run plays, it must come up on the finished message and leave the run playing. The
messages it clicks are made taller than the pane first, so a pane that moved and stayed there
cannot be the luck of a session that fits on screen. One check pins the CSS behind the whole
thing rather than the model of it: the rule that hides an unrevealed message must take it out
of the layout, because a message that is merely invisible is still room the run has not
earned. A framed tool-call box is sampled on either side of the exact instant it becomes real
— 50 ms before its first argument token it must be hidden, at the token it must be visible,
and once the playhead goes back past the message it must be hidden again — and a run played to
the end must show every call it made, so the rule cannot be satisfied by simply never showing
one. One check reads the pane's padding out of the built page instead of repeating it, because
the follow rule has no number of its own any more — it scrolls to the end of the pane, and the
cushion decides how high that leaves the newest line — and that check also holds the padding
to `min(vh, px)`: a cushion is welcome, an unbounded one or a fixed one is a pane that cannot
read itself on a short or a tall window.

After the handlers it walks the whole corpus, not just the scenario the URL picked, and holds
every entry to the same shape: it opens on a user turn and closes on a tool-free assistant
turn, every tool result answers a call that named that tool, there are at least three
requests, context never shrinks except at a compaction, and the phase split the summary quotes
is the split the corpus measures. It also pins the panel: the summary is the first card, the
requests history follows it above the controls, its
first two rows are `total` and `prefill : decode`, its phase rows pair tokens with time, every
row carries a hover note, and a row that describes a setting only appears while that setting is
on — which also means the checks restore the URL profile before reading the markup, so they
describe the page rather than whatever the UI probe tested last. Adding a scenario that does not
satisfy them fails here rather than in the dropdown.

Three rules keep the harness itself honest. A failing check fails the run: `ok` counts failures and
the process exits non-zero, because a harness that prints `FAIL` and exits 0 tells whatever is
watching exit codes that the build is fine. The shim memoizes attribute-selector lookups, so a
test that re-queries `[data-curve]` gets back the very nodes the page attached
its listeners to. Before that, a battery dispatching clicks on freshly built buttons drove nothing
and stayed green — which is how the curve presets went untested while looking tested. And when the
file under test is `index.html` itself, the harness rebuilds `src/` in memory and fails if the two
disagree, so a hand edit to the artifact is caught rather than quietly overwritten later.

node tools/selftest.mjs index.html "?session=long-log&autoplay=0"
